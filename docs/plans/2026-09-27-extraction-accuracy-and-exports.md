# Extraction accuracy, CSV export and linked PDF claims

Spec: the user's request of 27 September 2026 (extraction accuracy for merchant/date/currency; CSV and PDF export; receipt appendix with clickable internal links and a hidden `expenseapp://receipt/` deep link). No separate spec document exists; this plan is the argument from that request.

## Global Constraints

- Local-first: nothing in these tasks may add a network call, account, telemetry or CDN. Online AI stays opt-in and uses the existing OpenAI-compatible provider path.
- Stack stays as is: Tauri v2, Rust (`src-tauri/src`), React + TypeScript (`src`), SQLite, pdf-lib, Tesseract.js. No new heavy dependencies; a new crate or npm package needs a one-line justification in the task report.
- Money stays integer minor units (`i64`) using `domain::expense::currency_exponent`; never floats for stored amounts.
- Dates are stored as ISO `YYYY-MM-DD`. Ambiguous numeric dates (both parts ≤ 12) resolve **day-first (DD/MM/YYYY)** — Malaysian/global default — except when the receipt currency is `USD`, which resolves month-first. An unambiguous date (one part > 12) always uses the only valid reading. Ambiguous resolution lowers the date confidence to at most 0.5 so the UI flags "Verify".
- Currency symbols map to ISO codes: `RM`/`rm`/`Rm` → `MYR`, `S$`/`SGD` → `SGD`, `US$` → `USD`, `€` → `EUR`, `£` → `GBP`, `¥` → `JPY` only when no `CN`/`RMB`/`CNY` cue (then `CNY`), `₹` → `INR`, `฿` → `THB`, `Rp` → `IDR`, `₩` → `KRW`. A bare `$` resolves to the user's default currency if that is a dollar currency, otherwise stays unknown. Only currencies accepted by `currency_exponent` may be saved.
- A single bad field must never discard the whole extraction: invalid fields become `null` with confidence `0`, the rest is kept.
- Existing behaviour that must keep working: manual edits survive re-extraction; the offline fallback message on provider errors; the 30-page PDF receipt limit; the 100 MB report limit; the export-directory copy; all existing tests (17 Rust, 8 Vitest, 2 Playwright).
- Commands: Rust via the project toolchain (`export CARGO_HOME="$PWD/.tools/cargo" RUSTUP_HOME="$PWD/.tools/rustup" PATH="$PWD/.tools/cargo/bin:$PATH"`). Before each commit: `npm run format:check`, `npm run lint:rust`, `npm run test:rust`, `npm test`, `npm run build`. Regenerate TS bindings with `npm run bindings` whenever a `#[derive(TS)]` type or command signature changes, and commit `src/bindings/generated`.
- CSV output: RFC 4180 (comma separated, `"` quoting with doubled quotes, CRLF line endings), UTF-8 with BOM (Excel), amounts as plain decimals with the currency's exponent and `.` separator (no thousands separators), dates `YYYY-MM-DD`. Cells beginning with `=`, `+`, `-`, `@`, tab or CR are prefixed with `'` to prevent spreadsheet formula injection (except the numeric amount columns, which are generated by the app).

## Task 1: Rust field sanitiser (fallback parsing layer)

Create `src-tauri/src/services/extraction/sanitize.rs` and register it in `services/extraction/mod.rs`.

Public API:

- `pub fn normalize_currency(raw: &str, default_currency: &str) -> Option<String>` — trims, upper-cases, maps symbols/aliases per Global Constraints, returns an ISO code accepted by `currency_exponent`, else `None`.
- `pub fn normalize_date(raw: &str, currency: Option<&str>, today: chrono::NaiveDate) -> Option<(String, bool)>` — returns `(YYYY-MM-DD, ambiguous)`. Accepts: `YYYY-MM-DD`, `YYYY/MM/DD`, `YYYY.MM.DD`; `D/M/YYYY`, `D-M-YYYY`, `D.M.YYYY` with 1- or 2-digit day/month; 2-digit years (`27/09/26` → 2026; years 00–69 → 20xx, 70–99 → 19xx); month names/abbreviations in English and Malay (`27 Sep 2026`, `27-SEP-26`, `Sep 27, 2026`, `27 Sept 2026`, Malay `Jan Feb Mac Apr Mei Jun Jul Ogos Sep Okt Nov Dis`); surrounding text/time (`Date: 27/09/2026 14:05`). Rejects dates before 2000-01-01 or more than 1 day after `today`.
- `pub fn sanitize(result: Extraction, default_currency: &str, today: chrono::NaiveDate) -> Extraction` — normalises `currency` and `date` with the functions above (date uses the normalised currency as hint); trims merchant, collapses internal whitespace, strips leading/trailing punctuation, caps at 200 chars, drops merchants with fewer than 2 letters; drops a negative/over-`MAX_MONEY` total or tax, drops tax greater than total; drops a category not in `CATEGORIES` (becomes `None`); clamps every confidence into `0..=1` (non-finite → 0) and inserts missing confidence keys (`merchantName,date,total,tax,currency,category`) as 0; sets confidence 0 for any field it nulls; caps date confidence at 0.5 when ambiguous.

Wire-in: in `jobs/worker.rs` `complete_extraction`, call `sanitize(result, &settings.default_currency, today)` before `normalizer::validate`, for both online and offline sources. `normalizer::validate` stays as the final guard.

Tests (in the module, `#[cfg(test)]`): at least one case per accepted date format; `03/04/2026` → `2026-04-03` ambiguous with MYR and `2026-03-04` ambiguous with USD; `13/04/2026` → `2026-04-13` not ambiguous regardless of currency; `04/13/2026` → `2026-04-13`; future and pre-2000 rejected; `RM`, `rm`, `S$`, `US$`, `€`, `£`, `$` with MYR default (→ `None`) and with SGD default (→ `SGD`); `sanitize` keeps valid fields while nulling a bad date; tax > total dropped; missing confidence keys filled.

## Task 2: Offline OCR parser accuracy

- Merchant: scan the first 8 non-empty lines; skip lines that are mostly digits/punctuation, look like dates, times, phone numbers (`Tel`, `Phone`, `+60`, digit runs ≥ 7), registration/tax numbers (`SST`, `GST`, `Reg`, `Co.
